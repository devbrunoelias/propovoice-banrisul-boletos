⚠️ 3 pontos que ainda preciso te alertar

1. Isso agora vai quebrar um link que passou despercebido no diagnóstico anterior

Na tela admin (render_generate_page, listagem "Últimos boletos gerados"), a coluna "PDF" tem:
<a href="<?php echo esc_url($boleto['pdf_url']); ?>" target="_blank" rel="noopener">Abrir PDF</a>

Esse link aponta para a URL direta (pdf_url), não para o handler protegido. Com o .htaccess ativo, qualquer clique nesse link agora vai retornar 403, inclusive para você como admin. Corrija trocando esse link para passar pelo mesmo endpoint com token:
add_query_arg([
    'action' => 'pbb_download_boleto',
    'invoice_id' => absint($boleto['propovoice_invoice_id']),
    'token' => (string)($boleto['propovoice_invoice_token'] ?? ''),
], admin_url('admin-post.php'))

(mesma lógica já usada em render_boleto_shortcode). Também recomendo, já que o campo pdf_url na prática não deveria mais ser usado para acesso direto, considerar removê-lo do que é exibido/exposto e manter só pdf_path internamente — o pdf_url vira um resquício que só engana quem olhar o código depois.

2. Proteção manual = não versionada, não portátil

Esse .htaccess foi criado manualmente por você, fora do controle do plugin. Isso significa:

Se o site migrar de servidor, se a pasta banrisul-boletos for recriada (ex.: depois de uma limpeza de uploads, uma migração, uma nova instalação do plugin em outro site), o arquivo não existirá automaticamente — e ninguém vai lembrar de recriá-lo manualmente.
wp_mkdir_p($dir) em save_pdf_from_base64() não gera nada de proteção quando cria a pasta pela primeira vez.

Recomendo automatizar isso no próprio código (idealmente no PBB_Activator::activate() e também como fallback dentro de save_pdf_from_base64(), verificando se o .htaccess existe antes de salvar o PDF e recriando se necessário):
private static function ensure_protected_dir(string $dir): void
{
    if (!file_exists($dir . '/.htaccess')) {
        file_put_contents($dir . '/.htaccess',
            "<IfModule mod_authz_core.c>\nRequire all denied\n</IfModule>\n" .
            "<IfModule !mod_authz_core.c>\nOrder Allow,Deny\nDeny from all\n</IfModule>\n" .
            "Options -Indexes\n"
        );
    }
    if (!file_exists($dir . '/index.php')) {
        file_put_contents($dir . '/index.php', '<?php // Silence is golden');
    }
}

O index.php vazio é uma segunda camada — útil em configurações onde AllowOverride está desabilitado no host (nesse caso o .htaccess é silenciosamente ignorado pelo Apache, sem erro nenhum) ou se o mod_rewrite/mod_authz_core não estiver carregado como esperado.

3. .htaccess não existe no mundo Nginx

Se esse site (ou um cliente futuro que use este plugin) rodar em Nginx puro ou LiteSpeed sem emulação de .htaccess, essa regra não faz nada, e o silêncio é o problema: não há erro, o arquivo simplesmente fica público de novo sem aviso. Vale documentar isso claramente (ex.: no readme.txt do plugin) e, se possível, adicionar uma rotina de autoteste: na tela de configurações, fazer um wp_remote_get() interno para uma URL de teste dentro da pasta protegida e alertar o admin visualmente se o retorno não for 403/401.

Teste rápido que eu faria agora, antes de considerar isso fechado: tente abrir a URL direta de um PDF já gerado (.../wp-content/uploads/banrisul-boletos/boleto-XXXX.pdf) no navegador — deve dar 403. Depois clique em "Abrir PDF" na tela admin — hoje vai dar 403 também (item 1 acima), e no shortcode público (que já usa o handler com token) deve continuar funcionando normalmente.
